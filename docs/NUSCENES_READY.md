# After the nuScenes download finishes

The local `data/nuscenes` link points to `~/data/nuscenes`. Nothing in these
instructions is scheduled to run automatically. Setup has not run conversion or
training, even if the download completes while setup is in progress.

## Required raw layout

```text
data/nuscenes/  -> ~/data/nuscenes/
├── maps/
├── samples/
│   ├── LIDAR_TOP/
│   └── CAM_*/                 # All six camera channels
├── sweeps/
│   ├── LIDAR_TOP/
│   └── CAM_*/
└── v1.0-trainval/             # Full metadata JSON tables
```

Extract all training/validation blob archives into the same dataset root; avoid
an extra nested `nuscenes/nuscenes` directory. Keep the maps from the full metadata
release. Mini alone is not sufficient. The test split is unnecessary for this
train/validation preparation. On a different machine, create the local link with
`ln -s /absolute/path/to/nuscenes data/nuscenes` after creating `data/`.

## Checklist and exact commands

1. Wait for **all** trainval archive downloads and extraction to complete and
   verify the archives against the publisher's checksums. A completion marker or
   the existence of `samples/` alone does not establish completeness.
2. Activate the prepared environment and rerun the synthetic operator check:

   ```bash
   cd ~/sensor-fusion
   source scripts/activate_transfusion.sh
   python scripts/check_environment.py
   ```

3. Validate raw metadata and the presence/nonzero sizes of referenced LiDAR and
   camera files. This does not generate any data:

   ```bash
   python scripts/prepare_nuscenes.py
   ```

4. Generate info files, 2D annotations, and the object-sampling ground-truth
   database using **this checkout's old converter**:

   ```bash
   python scripts/prepare_nuscenes.py --run
   ```

   The wrapper checks input first, refuses to overwrite existing preparation
   outputs, and skips the stock CLI's mandatory test-split pass. It expects
   28,130 train and 6,019 validation infos. Allow additional disk space and time
   for the GT database. If interrupted, move partial generated outputs aside
   before repeating; do not remove the raw input folders.

   Expected outputs under `data/nuscenes/`:

   ```text
   nuscenes_infos_train.pkl
   nuscenes_infos_val.pkl
   nuscenes_infos_train.coco.json
   nuscenes_infos_val.coco.json
   nuscenes_dbinfos_train.pkl
   nuscenes_gt_database/
   ```

   Do not reuse infos generated by a recent MMDetection3D release: upstream
   explicitly warns that changed yaw/box conventions can give incorrect metrics.

5. Review the [3080 plan](RTX3080_PLAN.md). No upstream configs were changed.
   Start with LiDAR-only unless you have assembled the pretrained components
   required by the fusion stage. Decide on batch size, LR, and memory tradeoffs;
   test a few real batches and validation samples before a long run.
6. When **you are ready to start training**, this example applies batch/LR
   overrides without editing the original config (not executed during setup):

   ```bash
   python tools/train.py configs/transfusion_nusc_voxel_L.py \
     --gpu-ids 0 --launcher none \
     --work-dir work_dirs/transfusion_l_3080 \
     --cfg-options data.samples_per_gpu=1 data.workers_per_gpu=2 \
       optimizer.lr=0.00000625
   ```

   This is an FP32 starting point, not a proven 12 GiB memory guarantee. Monitor
   peak VRAM and finite loss; adjust after a short real-data run. Do not add
   `--autoscale-lr` to this explicitly scaled example. FP16 and accumulation
   need the additional validation/implementation described in the 3080 plan.
7. For camera fusion, first finish the LiDAR pretraining, obtain/train compatible
   image weights, build and inspect a matching initialization checkpoint, then
   update `load_from` and review the intended frozen modules before the six-epoch
   stage. The supplied `fusion_voxel0075_R50.pth` path is a missing prerequisite,
   not a downloadable model shipped with this repository.
